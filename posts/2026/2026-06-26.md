I asked Claude, Gemini, and ChatGPT to define vibe coding and then had Claude synthesize the three responses into a summary. Here is that summary, which I've edited for length:

> Vibe coding is a style of software development in which a human primarily guides an AI—through natural-language prompts, interactive chat, or coding agents—to generate the actual code, rather than writing the syntax line by line. The developer works at a higher level of abstraction, focusing on intent, architecture, logic, and product goals while acting as some combination of director, architect, and code reviewer. Development becomes a conversation: you describe what you want, the AI does the heavy lifting, and you iterate rapidly—spinning up prototypes, refactoring, and adding features far faster than manual coding would allow. This lowers the barrier to entry for non-technical creators while letting experienced engineers move at accelerated speed.
>
> The defining shift is from authoring code to directing and evaluating it: natural language becomes the primary interface, and the human's role centers on describing intent, then testing, reviewing, and steering the results. Good vibe coders still review code, write tests, and understand the architecture; the AI just handles the typing. Either way, it's generally distinguished from simply using AI autocomplete and it isn't strictly a beginner's tool—experienced engineers often get the most leverage, since they know what to ask for and how to validate what comes back.

I then asked all three LLMs to define pair programming. All three gave me nearly the same reply, which I felt was best rendered by Claude:

> Pair programming is a software development practice where two programmers work together at a single workstation (or share a screen when remote), collaborating in real time on the same code. It comes out of the Extreme Programming (XP) movement and has been around since the late 1990s.
> The two people take on distinct, complementary roles:
> - The driver writes the code — controlling the keyboard and focusing on the tactical, line-by-line work of getting something typed out.
> - The navigator reviews each line as it's written, thinks about the bigger picture, watches for errors, and considers the overall direction and design.

I've been thinking about this today because I've spent the past couple of weeks creating, with the help of Claude, several custom modules for the Drupal websites I develop and maintain at work. While a few modules have been relatively simple builds – consolidating code duplicated across modules and Drupal installations into modules that define services my other modules can use – one of the modules has turned into a large, complicated undertaking. The module is named `verify_journals` and it is intended to aid management of website content.

Two of my websites have a node type `journal`. This node type describes scholarly journals. Each node contains the title of the journal, a link to the journal website (if known) and the journal ISSN (International Standard Serial Number). The ISSN serves as the unique identifier for journal nodes. However, complications arise because journals may have more than one ISSN. Typically, a journal has a print version and an online version. Each version is assigned a different ISSN. In addition, if a journal’s title has changed, the ISSN may be retired and a new ISSN assigned. To reliably identify a journal based on ISSN, I need to make sure each journal node includes all of the ISSNs for that journal and than all the ISSNs are valid. Journal nodes are most often created through automated processes – Feeds or imports from external APIs – so I need a way to review all journal nodes after they are created.

Fortunately, [OpenAlex](https://openalex.org) provides an API with a `sources` endpoint that can be used to look up journals based on ISSN. I can use this endpoint to:

- verify that each ISSN points to the correct source; and
- gather the other ISSNs from the source record to add to the corresponding journal node.

The `verify_journals` module provides quite a few functions:

- a database table `verify_journals_verified` for recording the node number of each journal node which has been verified
- a QueueWorker which checks the ISSNs from each journal node against information in OpenAlex
- custom node tasks (with corresponding Controllers) for
  - queueing individual nodes; and
  - manually marking individual nodes as verified
- A Form for queueing groups of nodes
- A Form for manually checking ISSNs against OpenAlex
- A views plugin filter to create queries of the `verify_journals_verified` table

I have previously developed custom modules that use Forms, Controllers, and QueueWorkers, but I've never created custom node tasks or views plugins. For these pieces, I was able to search for and read information that generally described the development process and provided examples. However, most Drupal documentation leaves a significant gap between the explanation and the ability of a programmer of my level to execute. Claude was the key to bridging that gap, writing code that I was then able to understand, review, and annotate with comments. In other cases, I would write the classes and functions I needed. The I would ask Claude to perform the review of my work.

So this is vibe coding, but it also feels a bit like pair programming. Some of the time, Claude is the driver, producing the lines of code while I serve as the navigator. Other times, I am driving and leaning on Claude for at least some of the navigation. It is a model for interaction with LLM-based coding that I am becoming more and more comfortable with. I gain the efficiency benefits of working with an LLM while at the same time trying to benefit from the knowledge sharing component of the pair-programming experience. 

As the responsible party, I must understand and review all code that is deployed to the websites I maintain. As an employee of a large institution, it is important that I am familiar with and am making use of the appropriate tools for performing my work – and LLMs are becoming a critical tool. And, as someone who wants to continue to have a career in web development, it is critical for me to continually improve my skills – not surrender them to coding agents. I feel like the approach I've developed is helping me balance these concerns. That approach seems to sit somewhere between where vibe coding ends and pair programming begins – albeit with the LLM serving as other part of the pair.
